## 1. ☠️ 在真正的高缩放屏上验一次 Qt6 的 HiDPI

**欠了什么**：PyQt6 迁移（CLAUDE.md 第 43/44 条）已经落地并推上 master，
但**开发机是 100% 缩放**，所以整条 HiDPI 路径从没在真实的 125%/150% 屏上
跑过一次。目前的证据都是间接的：

- 第 43 条那张 `logicalDPI / DPR / screen_scale_factor()` 的表，是用
  `QT_SCALE_FACTOR` / `QT_FONT_DPI` **模拟**出来的，不是真屏幕。
- `window_geometry.rescale_state_for_dpr()`（Qt5 存档 → Qt6 坐标空间的换算）
  只有单元测试。真机上跑到的一直是 `saved_dpr == current_dpr` 的短路分支——
  **真正的换算代码在生产环境里一次都没执行过**。

**为什么值得单独记一条**：这是全项目唯一一条「会让已经在用的老用户看出
差别、而日志里什么都看不到」的路径。150% 的笔记本上如果换算错了，现象是
悬浮窗和字一起涨 50%，用户只会觉得"更新完变难看了"，不会来报 bug。

**怎么验（十分钟）**：找一台 125% 或 150% 缩放的 Windows 笔记本——

1. 带上一份**老的** `window_state.json`（Qt5 时代存的，没有 `coord_dpr` 字段；
   或者手动把那个字段删掉来模拟），放进仓库根目录。
2. `venv\Scripts\python main.py` 起一次。
3. 看两件事，**就这两件**：
   - 悬浮窗的物理尺寸和字号，跟 Qt5 时代**看起来一样大**吗？
     （涨了 ~50% = 换算没生效；缩了 ~33% = 多除了一次 devicePixelRatio）
   - 关掉程序，看新写回的 `window_state.json` 里有没有 `coord_dpr`，
     值等不等于那块屏的实际缩放倍率（150% → 1.5）。
4. 顺手把 `⚙` 面板打开看一眼字号（`panel_font_px`）有没有崩。

**做完之后**：把实测数字补进 CLAUDE.md 第 43 条那张表，并把第 44 条末尾
「没验的」那一段删掉。如果发现是错的——那比改代码更值钱的是先把现象
写下来，再动 `rescale_state_for_dpr`。

## 2. 悬浮窗 chrome 的字号没跟着缩放

CLAUDE.md 第 24 条里一直挂着的老账：正文字号和设置面板都按倍率走了，
**按钮条等其它 chrome 的字号还是写死的像素值**。Qt6 接管缩放之后这条
大概率自动好了（Qt 会统一放大），但同样没在真屏幕上确认过——
和第 1 条一起验，别单独跑一趟。
