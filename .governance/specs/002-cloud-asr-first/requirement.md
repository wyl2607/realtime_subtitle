# 002 云端识别优先（Groq Whisper → mini2 → Windows → 本机）

- 状态：用户已确认（2026-10-09；验收数字按 Claude 建议定稿，含额度提前切走阈值 90%）
- 日期：2026-10-09
- 仓库 / 分支：realtime_subtitle · `feat/macos-native`（当前 e9646d6，Sprint 001 收尾中：TK-005b 进行中、TK-007 验收准备）
- 前置：Sprint 001 的协议约定 P1–P8 已冻结。本需求作为 **Sprint 002**，在 001 收尾后开工；需要改 P6（节点清单）/ P7（路由打分）的地方，在 002 的 RFC 里写成新版本，不回头改 001。

## 1. 目标

1. **识别默认先用 Groq 云端 whisper-large-v3。** 它是 rslite 路由里优先级最高的一个「云端节点」。
2. **Groq 不可用时，字幕不中断，自动按顺序回退**（用户 2026-10-09 已定）：
   1. Groq 云端
   2. mini2 节点
   3. Windows 节点（节点本身属于下一期，本期只要求路由能自动接上它）
   4. 本机 Apple 识别（B）
   - 「Groq 不可用」指：当天额度用完、返回 429/5xx、请求超时、断网，或者用户关掉了云端开关。
   - **本期不把 Cloudflare 排进回退顺序**（用户 2026-10-09 已定）。
3. **Groq 恢复后自动切回 Groq。** 例如第二天额度重置，或网络恢复。复用 001 的规则：在静音点切换，不重复、不丢句。
4. **翻译不变**，继续走现有的 Apple 系统翻译。

## 2. 动机（2026-10-09 实测）

测试用和 001 相同的 60 条 FLEURS 德语录音、相同的打分方法（`asr_bench.norm` + jiwer）。数据在 `~/projects/rs-mac-native-data/cloud_*.jsonl`，脚本是同目录下的 `cloud_asr.py`。

| 方案 | WER | 每条耗时（平均 14s 音频） |
|---|---|---|
| **Groq whisper-large-v3** | **3.62%** | p50 0.52s / p90 0.82s |
| Groq whisper-large-v3-turbo | 6.00% | p50 0.37s |
| Cloudflare whisper-large-v3-turbo | 4.05% | p50 2.0s / p90 5.7s |
| 本机 MLX turbo fp16（001 之前的最好成绩） | 4.05% | RTF 0.185 |
| 本机 Apple 识别（B） | 7.38% | RTF 0.017 |

- **Groq large-v3 比本机所有方案都准、都快，而且本机不用跑模型。** 用户实际遇到过 M2 16GB 跑 Whisper 过热。
- **要选 large-v3，不选 turbo。** Groq 的 turbo 比本机同名模型差约 2 个百分点。
- **注意：** 这次测的是录好的整句文件。实时切段后的准确率要在验收里重新测。001 里 mini2 测出的 2.6% 用的是另一份 67 秒测试，不能和上表直接比。

## 3. 约束

- **隐私（与 001 不同，用户 2026-10-09 已定：默认开，可关）**
  - 云端识别默认开启。界面上要明显标出「云端」，让用户知道音频正在上传给 Groq。
  - 设置里可以一键关掉。关掉后完全不连 Groq，只走 mini2 / Windows / 本机，也就是 001 原来的「音频只走内网」行为。
  - 不落盘音频。key 不写进仓库、日志和崩溃报告。
  - ⚠️ 仓库 README 和 CLAUDE.md 开头都承诺「完全本地运行、不向任何云端发送音频」。这项功能会打破这个承诺，所以文档必须同步改写，写清楚：只有 rslite 默认上传，A 版不变，以及怎么关掉。不能只改代码。
- **Groq 计费和免费额度**（官方文档 / 控制台，2026-10-09）
  - 每次请求**最少按 10 秒音频计费** → 必须按 VAD 整句或整段发，避免发零碎短段；具体切段策略在 draft 里定。
  - 免费档 whisper-large-v3：每分钟 20 次、每天 2000 次、每小时 7200 音频秒、每天 28800 音频秒（8 小时），单个文件不超过 25MB。
  - 客户端要自己记已用的音频秒数（每次按 `max(10, 响应里的 duration)` 记）和请求次数，**任一上限（每分钟 20 次 / 每小时 7200 音频秒 / 每天 2000 次 / 每天 28800 音频秒）用到 90% 就提前切走**，不要等到被 429 才切。
  - 2026-10-09 实测响应头：只有请求次数配额（`x-ratelimit-limit-requests` / `-remaining-requests` / `-reset-requests`），**没有音频秒数配额头**；`reset-requests` 显示的是几十分钟级的恢复时间，说明额度是**滚动窗口逐步恢复**，不是每天零点一次性重置。音频秒数的恢复方式在 draft 里再核实（官方文档 / 撞一次 429 看 `retry-after`）。
- **凭据**：从 `GROQ_API_KEY` 读取（各机已放在 `~/.config/groq/env`，由 `~/.zshenv` source）。GUI 程序不一定会继承 shell 的环境变量，读取方式在 draft 里定。没有 key 时这个节点自动视为不可用，不报错打扰用户。
- **复用 001，不另起炉灶**：节点清单（P6）、路由打分与故障回退（P7）、静音点迁移、带时间句子与混合替换（P4/P5）、本机档门槛（P8）。Groq 只是多一种节点类型。
- **本机不跑大模型**：在 MacBook Air 上，Groq 路径只能用轻量的 VAD 切段和网络上传，不能加载 Whisper。
- **兼容**：不破坏 A 版（Python 桌面字幕，Windows/Mac）现有行为，也不破坏 001 已经验收的 mini2 节点流程。
- **网络**：本机走 Surge 代理（127.0.0.1:6152），实现要遵守系统和环境变量里的代理设置。

## 4. Done criteria

1. **默认走 Groq**：rslite 在德语直播或回放中默认用 Groq large-v3，界面显示「云端」。
2. **准确率**：用 001 的 67 秒回放和 FLEURS 60 条，按实时切段方式跑。
   - FLEURS 60 条：WER **≤ 4.5%**（整句文件是 3.62%，留约 0.9 个百分点给实时切段）。
   - 67 秒回放：WER **不高于 001 混合档的最终文本 WER**。具体数字等 Sprint 001 的 TK-007 跑出后填进这里；TK-007 出数前，暂以 mini2 在同一份 67 秒回放上测出的 2.6% 作参考。
3. **延迟**：每段说完（VAD 判定段尾）到识别结果出现在界面上，中位数 **≤ 2s**（不含翻译）。
4. **回退**：下面每种场景都要测，字幕不断、不重复、不丢句，日志写明切换原因：
   - 拔网线
   - 填一个错误的 key
   - 模拟 429
   - 模拟当天额度用完
   - 关掉云端开关
   - mini2 也离线（这时应该落到本机 B）
5. **恢复**：故障消失后在下一个静音点自动切回 Groq。
6. **额度**：连续跑 1 小时直播，全程不触发被动 429，并且：
   - 请求次数：本地记账和响应头 `x-ratelimit-remaining-requests` 的前后差值**完全一致**。
   - 音频秒数：本地记账和 Groq 控制台用量的偏差 **≤ 5%**。响应头不提供音频秒数，如果控制台也看不到逐小时用量，就改为核对「本地记账 = Σ max(10, 每次响应的 duration)」的计算本身，并在验收文档里写明是这种退回的核对方式。
7. **测试**：pytest / swift build / ruff 全绿；新增单测覆盖切段和计费下限、额度记账、回退顺序、开关。
8. **文档**：README 写明云端开关、隐私说明、key 配置方法。
